# HINA OTA

## 실행 경로

- Windows 비서는 기존 캐릭터 클릭으로 기본 브라우저의 AI-Studio를 연다. Windows 트레이·입력·알림과 원격 애니메이션 캐시는 기존 실행기가 담당한다. 웹 기능 변경은 Pages로 배포한다.
- PC와 모바일 브라우저는 같은 PWA와 반응형 대시보드를 사용한다. 브라우저의 설치 또는 홈 화면 추가 기능으로 시작할 수 있다. 향후 Android는 검증된 HTTPS 출처를 여는 Trusted Web Activity를 우선 검토한다. 앱 서명 지문과 도메인 소유권이 확정되면 Digital Asset Links를 연결하며, 권한·설치기 변경은 OS 및 스토어 배포 절차를 따른다.

## 업데이트 동작

첫 접속은 Pages의 HTTPS 설치본을 즉시 연다. 서비스 워커는 별도 작업으로 초기 파일을 검증하고 저장한다. 이후 안정·개발 채널은 고정 Ed25519 공개 키로 매니페스트 서명을 검증한다. 프로토콜, 빌드 순서, 파일 경로·크기·SHA-256을 확인한다. 해시 캐시에서 검증된 바이트를 찾으면 다운로드를 생략한다. 앱은 GitHub API 대신 Pages에서 매니페스트를 읽으며 채널당 30분 간격으로 확인한다.

모든 파일을 검증하면 준비 상태로 기록한다. 히나가 캐릭터 알림과 업데이트 브리핑을 표시한다. 앱을 새로 열거나 사용자가 **다시 열어 적용**을 선택할 때 적용한다. 열린 탭에는 버전별 URL로 기존 파일을 제공한다. 적용할 수 없으면 정상 버전을 유지하고, 캐시가 손상된 활성 버전은 다음 시작에 이전 정상 버전으로 복구한다. **이전 버전 복원**으로 직접 되돌릴 수 있다. 브라우저 캐시 전체가 삭제된 경우 온라인에서 다시 시작해야 한다.

업데이트 이력은 브라우저의 OTA 저장소에 남기고, 역대 출시 기록은 Git에서 관리한다. HINA MIND의 경험·검증 이력은 CORE가 관리한다. CORE 공개 집계는 별도 경로에서 갱신하며 오프라인에서는 최근 정상 집계를 읽는다. 체크포인트, 개인 기억, 사용자의 브라우저 설정을 콘텐츠 패키지에 넣거나 OTA 캐시와 함께 교체하지 않는다.

## 릴리스 준비

1. 각 채널의 Ed25519 개인 키를 보안 저장소에서 생성한다. 공개 키는 SPKI DER의 Base64로 변환해 `ota/trust.js`의 해당 채널에 고정한다.
2. GitHub의 `github-pages` 환경에 `HINA_OTA_STABLE_KEY`와 필요한 경우 `HINA_OTA_DEVELOPMENT_KEY`를 설정한다. 값은 대응하는 개인 키 PKCS#8 DER의 Base64다. 저장소 파일과 로그에 개인 키를 남기지 않는다.
3. 개발 후보를 배포하려면 검토한 원격 브랜치 이름을 환경 변수 `HINA_OTA_DEV_REF`에 지정한다. 기본 설치 경로는 안정 채널이다. 공개 브리핑은 `ota/release-note.txt`에 기록하고 소스와 함께 버전 관리한다.
4. Pages 작업에서 서명한 안정·개발 매니페스트와 해시별 파일을 배포한다. 공개 키가 아직 없는 최초 설정에서는 HTTPS PWA 설치본만 배포된다. 활성 서명 키가 매칭되지 않으면 배포 작업이 실패한다.

릴리스는 서비스 워커 프로토콜, 콘텐츠 해시, 기능 모듈 해시, 지능 정의 해시, 데이터 스키마를 구분한다. 학습 전략은 CORE 검증·승인 절차를 따르며 공개 집계가 전략을 설치하는 권한을 갖지 않는다. 원격 웹 기능은 Tauri 명령 접근 권한을 받지 않는다. PC 실행기의 자동 빌드는 Tauri 소스·권한과 실행기 의존성·번들 절차 변경에 한정한다. 기존 설치본의 내장 화면을 의도적으로 교체해야 하면 수동 Windows 릴리스를 사용한다. 향후 Android 실행기 변경도 별도 OS 또는 스토어 배포 절차를 따른다.
